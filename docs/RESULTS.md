## 0. 채점 버그 정정 (2026-11)

**이 문서 §1~§3의 KOBEST 수치(†)는 선택지 첫 토큰을 빠뜨리는 버그가 있는 채점기로
측정했습니다.** perplexity, 사실 프로브, 대화 평가(정답률·멈춤·반복)는 생성 기반이라
영향이 없습니다.

### 무엇이 틀렸나

KOBEST는 문맥 뒤에 선택지를 이어붙여 로그확률을 비교합니다. 채점 시작 위치를
`len(encode(문맥))`으로 잡았는데, 문맥이 공백으로 끝나면 pretokenizer가 그 공백을
선택지 첫 단어에 붙입니다.

```
encode("…\n답: ")    → [… ":", " "]       ← 끝 공백이 혼자 토큰 하나
encode("…\n답: 예")  → [… ":", " 예"]     ← 공백이 '예'에 붙었다
```

그래서 경계가 한 칸 뒤로 밀려 **선택지의 첫 토큰이 항상 채점에서 빠졌습니다.**
실제 64K 토크나이저로 확인한 결과입니다.

| 과제 | 선택지 | 버그 채점기가 본 토큰 | 채점해야 할 토큰 |
|---|---|---|---|
| BoolQ | 예 | **(없음)** | ` 예` |
| BoolQ | 아니오 | `오` | ` 아니` `오` |
| COPA | 땅이 젖었다. | ` 젖` `었다` `.` | ` 땅이` ` 젖` `었다` `.` |
| HellaSwag | 개가 공을 쫓아간다. | ` 공을` ` 쫓아` `간다` `.` | ` 개가` ` 공을` ` 쫓아` `간다` `.` |

### 기록된 증상이 이것으로 설명됩니다

§5에 적은 "BoolQ 150문항 전부 '예'"와 §2의 "1,404문항 중 1,373개 '아니오'"는 서로
반대 방향이라 이상했는데, 둘 다 같은 버그의 결과입니다.

- **정규화 전**: '예'는 채점 토큰이 0개라 점수가 빈 합 = 0. '아니오'는 log P(오) < 0.
  0이 항상 크니 **문단과 무관하게 전부 '예'**.
- **비조건부 정규화 후**: '예'는 0 − 0 = 0. '아니오'는
  log P(오 | 문단…아니) − log P(오 | "답: 아니"). '아니' 다음 '오'는 문맥이 길수록
  확실해지니 대개 양수 → **대부분 '아니오'**.

즉 BoolQ 점수는 모델이 문단을 이해하는지와 무관하게 정해졌습니다. "BoolQ는 끝내
못 배웠다"는 결론은 근거가 없고, 실제 능력은 재측정해야 압니다. COPA·HellaSwag은
선택지 첫 단어(주로 주어 — "땅이", "개가")를 빼고 채점해서 신호 일부를 버렸습니다.
고친 뒤 점수가 오를지 내릴지는 재측정 전엔 알 수 없습니다.

§5의 교훈("점수가 안 움직이면 채점을 의심할 것")은 맞았지만, 그때 찾은 원인(흔한
선택지 편향)은 증상이었고 뿌리는 토큰 경계였습니다. 예측 분포를 센 덕분에 이상을
감지했고, 이번엔 **채점된 토큰을 직접 출력해 보고서야** 원인이 보였습니다.

### 고친 방법

문맥+선택지를 한 번에 토큰화하고 토큰의 바이트 길이를 누적해, 문맥 안에 완전히
들어가는 토큰까지를 문맥으로, 선택지에 한 바이트라도 걸치는 첫 토큰부터를 채점 대상으로
삼습니다(`eval.choice_span`). `tests/test_eval_scoring.py`가 실제 토크나이저로 "채점 토큰을
이어붙이면 선택지 전체"임을 검증합니다. 선택지를 한 번의 forward로 묶고 lm_head는 채점
위치에만 적용해 더 빨라졌고, 세 지표를 함께 기록합니다:
`acc_calib`(비조건부 정규화, 기본) · `acc`(로그확률 합) · `acc_len`(바이트 길이 정규화).

### 함께 고친 측정·학습 문제

| 문제 | 영향 | 수정 |
|---|---|---|
| val loss를 평가마다 **다른** 배치(약 8만 토큰)로 잼 | §5의 "val loss가 100 step 주기로 ±0.1 진동" 중 상당 부분이 표본 노이즈였을 수 있다 | 매번 같은 val 배치로 잰다 |
| annealing 구간에서 재개하면 로더 위치를 'step 번호'로 덮어씀 | 재개할 때마다 annealing 데이터 스트림이 되감겨 이미 본 배치를 다시 학습. 코드상 step 19,200 일시정지 후 재개한 첫 step은 직전 step과 마이크로배치 256개 중 255개가 같았다 | 저장된 로더 상태를 annealing 로더에 복원. 중단 없이 학습한 결과와 annealing 앞뒤에서 두 번 끊고 재개한 결과가 비트 단위로 같음을 e2e 테스트로 검증 |
| 무작위 윈도우 **복원추출** | 데이터 N 토큰에서 M 토큰을 학습하면 한 번이라도 본 비율은 1−e^(−M/N). 웹 구간 20.1B / 23.5B → **57%**, annealing 5.0B / 4.9B → **64%**. 나머지는 중복 샘플로 채워졌다 | `epoch` 모드(새 학습 기본값): 겹치지 않는 윈도우를 에폭마다 섞어 모든 토큰을 정확히 한 번씩. 예전 체크포인트는 random 모드 그대로 재개 |
| 초기화 시드 없음 | 같은 설정도 실행마다 다른 모델 | `seed` 설정(기본 1337) |
| annealing 직전 스냅샷이 저장 주기(100)와 안 맞음 | 학습을 멈추고 손으로 복사해야 했다(`pause_at_19200.sh`) | 전환 직전 step을 자동 스냅샷, `--stop-after N`으로 정확한 step에서 정지 |
| `sft_eval.py`가 `epoch0.pt`를 읽지만 `sft.py`는 만들지 않음 | 재현 시 평가가 죽는다 | 에폭마다 `epoch{n}.pt` 저장 |
| SFT gradient 누적이 마이크로배치 평균의 평균 | 답이 짧은 배치의 토큰이 더 큰 가중치를 받았다 | 토큰 가중 평균 |
| 대화 CLI가 기록을 무한히 붙임 | 2,048토큰을 넘는 순간 RoPE 테이블 밖으로 나가 크래시 | 오래된 턴부터 잘라 문맥 안에 맞춘다 |

## 1. 사전학습 추이 (KOBEST †)

4,000 step마다 스냅샷을 남기고 CPU로 자동 평가했습니다. **같은 조건으로 측정한 값끼리만**
비교해야 해서, 채점 방식을 바꾼 뒤에는 과거 스냅샷을 전부 재평가했습니다.

| step | 토큰 | perplexity | COPA | HellaSwag | BoolQ |
|---|---|---|---|---|---|
| 4,000 | 4.2B | 24.18 | 58.0% | 36.0% | 46.7%* |
| 8,000 | 8.4B | 19.33 | 60.7% | 40.7% | 46.7%* |
| 12,000 | 12.6B | 17.77 | 60.7% | 40.7% | 46.7%* |
| 16,000 | 16.8B | 16.62 | 64.0% | 43.3% | 46.7%* |
| 19,200 | 20.1B | 17.02 | 62.7% | 46.7% | 56.7%* |
| 20,000 | 21.0B | 14.68 | 62.7% | 38.7% | 56.7%* |
| 무작위 | | | 50% | 25% | 50% |

`*` 예측이 한쪽으로 90% 이상 쏠린 구간 — 점수가 성능이 아니라 라벨 분포를 반영합니다.

**8.4B~12.6B에서 벤치마크가 완전히 멈췄다가 16.8B에서 다시 올랐습니다.** 그 구간에도
perplexity는 계속 내려갔습니다. loss가 준다고 능력이 바로 따라오지 않고, 정체 구간이
있어도 학습은 진행 중이라는 뜻입니다.

## 2. annealing 효과 (전체 문항, GPU, 같은 조건 — KOBEST †)

마지막 20%(step 19,200~)에서 웹 중심 데이터를 끊고 위키·교과서 66% 혼합으로 바꿨습니다.

| | annealing 직전 (19,200) | 최종 (23,999) | 변화 |
|---|---|---|---|
| perplexity (웹 val) | 18.84 | **13.87** | −26% |
| perplexity (고품질 val) | 19.74 | **12.09** | −39% |
| COPA (n=1,000) | 66.3% | 67.1% | +0.8%p |
| HellaSwag (n=500) | 46.2% | **40.0%** | **−6.2%p** |
| BoolQ (n=1,404) | 49.9% | 50.0% | 무작위 |

**언어 모델링은 크게 좋아졌지만 HellaSwag은 실제로 떨어졌습니다.** 고품질 데이터로
학습했는데 웹 텍스트 예측력까지 26% 좋아진 건 기대 이상이었고, 반대로 HellaSwag
(일상 상황이 어떻게 이어지는지 고르는 과제)은 웹의 서사 텍스트를 줄인 대가로 보입니다.
다시 한다면 annealing 혼합에서 웹 비중을 24%보다 높게(40~50%) 잡겠습니다.

BoolQ는 전 구간 실패로 기록했습니다. 최종 모델은 1,404문항 중 1,373개(98%)를 "아니오"로
답합니다. ~~문단 내용에 따라 답을 바꾸는 능력이 끝내 생기지 않았습니다.~~
→ **정정(§0)**: 이 쏠림은 채점 버그('예'의 채점 토큰 0개)로 설명됩니다. 능력은 재측정 전까지 미확인.

## 3. SFT 결과 (KOBEST †, 대화 평가는 영향 없음)

베이스·에폭0·최종 세 모델을 **학습 데이터와 겹치지 않는 자체 문항**으로 비교했습니다.

| | 대화 정답률 | 스스로 멈춤 | 반복 루프 | COPA | HellaSwag | BoolQ |
|---|---|---|---|---|---|---|
| 베이스 | 71.0% | 92% | 11% | 67.1% | 40.0% | 50.0% |
| SFT 에폭0 | 67.7% | 100% | 3% | 66.9% | 40.8% | 49.9% |
| **SFT 최종** | **74.2%** | 97% | 8% | 66.4% | 40.8% | 50.4% |

| 유형 | 베이스 | SFT 최종 |
|---|---|---|
| 사실 (20문항) | 100% | 100% |
| 지시 (6문항) | 33% | 50% |
| 계산 (5문항) | 0% | 0% |

### SFT가 실제로 바꾼 것

**답을 마치고 멈추는 법**입니다. 반복 루프가 11% → 3~8%, 스스로 종료하는 비율이
92% → 97~100%가 됐습니다. 사전학습 내내 따라다니던 문제가 여기서 해결됐습니다.

지시 따르기도 개선됐습니다.

> **'Good morning'을 한국어로 번역해줘.**
> 베이스: '굿모닝'은 한국어로 '모닝'을 의미하는 말입니다. ✗
> SFT: "굿모닝"은 "좋은 아침"으로 번역할 수 있습니다. ✓

KOBEST는 거의 변하지 않았습니다. 학습률을 2e-5로 낮게 잡아 **사전학습 능력을 깎지 않은
것**이 확인됩니다.

### 베이스 모델이 이미 대화를 했습니다

베이스 모델이 처음 보는 사실 문제 20개를 전부 맞혔습니다. 같은 모델이 며칠 전
문장 이어쓰기 형식에서는 "물의 화학식은" → 0/10이었는데 말입니다.

차이는 **질문 형식**이었습니다. 모델은 지식을 갖고 있었고 꺼내는 방법이 문제였습니다.
베이스가 대화 형식을 아는 이유는 annealing 데이터에 instruction 대화를 4% 섞었기
때문인데, 그 결정이 **SFT의 효과를 상당 부분 미리 가져가 버렸습니다.**

### 주의: 차이는 작습니다

채점 문항이 31개라 1문제가 3.2%p입니다. 74.2%와 71.0%는 한 문제 차이입니다.
반복 루프만 보면 에폭0이 더 낫고(3% vs 8%), 검증 loss도 에폭0이 좋았습니다
(1.3149 vs 1.3297). **두 번째 에폭은 얻은 게 거의 없고 과적합 기미만 보였습니다.**

답하면서 "백두대간", "태백산맥" 같은 용어는 정확히 씁니다. 형식은 알고 내용은 모르는
상태입니다.

## 5. 과정에서 배운 것

**점수가 안 움직이면 채점을 의심할 것.** BoolQ가 세 스냅샷 연속 정확히 53.3%였습니다.
예측 분포를 세어보니 150문항 전부 "예"였고, 53.3%는 라벨 분포 그 자체였습니다.
이후 모든 벤치마크에 예측 쏠림 감지를 넣었습니다.

**측정 도구가 성능을 가릴 수 있다.** 로그확률 합으로 채점하면 짧은 선택지가 유리합니다.
GPT-3 논문의 비조건부 정규화를 적용하자 HellaSwag이 32.7% → 43.3%로 드러났습니다.
실력이 오른 게 아니라 **원래 그만큼이었는데 측정이 가리고 있었습니다.**

**한 번의 샘플로, 한 개의 체크포인트로 판단하지 말 것.** 같은 모델이 "서울"과 "도쿄"를
둘 다 답합니다. val loss가 100 step 주기로 ±0.1 진동해서, 하필 고점 체크포인트를
뽑으면 모델이 퇴보한 것처럼 보입니다. 실제로 한 번 그렇게 오진했고, 스냅샷 네 개를
나란히 놓고서야 진짜 그림이 보였습니다.

**코퍼스 크기를 추정하지 말 것.** parquet 압축 크기로 어림한 값과 스트리밍 앞부분
표본이 각각 3배, 5배 빗나갔습니다(위키백과 750M 추정 → 실제 260M). 실제 준비 실행의
산출량만 믿을 수 있습니다.

**평가 데이터와 학습 데이터를 분리할 것.** annealing에 SFT와 같은 데이터를 넣은 탓에
SFT 검증 loss가 일반화가 아니라 기억을 재고 있었습니다. 그래서 자체 문항을 만들고,
17만 개 학습 예제와 문자 3-gram으로 대조해 겹치는 2문항을 걸러냈습니다.

**공유 자원에서는 최적값보다 안전 마진.** 벤치마크가 고른 배치 4(34.7GB)는 다른 작업이
뜰 때마다 OOM으로 죽었습니다. 배치 2(26GB)로 낮추자 안정적으로 완주했고, 실제 처리량도
더 좋았습니다 — 벤치마크 자체가 다른 작업이 떠 있는 상태에서 측정된 값이었기 때문입니다.
